# 마스터 개별 테이블 연결

7개 마스터 종류를 개별 MySQL 테이블에서 조회·등록·수정·비활성화한다. 출하/청구/입금/재고/지급 데이터는 아직 preview_workspace JSON에 유지한다.

| 화면 | 실제 테이블 | 비고 |
|---|---|---|
| 得意先 | client_m | 고객 코드·명칭·마감일·비활성화 |
| 商品 | item_m | 상품 코드·명칭·단위·단가·비활성화 |
| 現場 | field_name_m | 고객+현장코드+가지번호 복합키 |
| 銀行 | code_m (`code_key=BANK`) | 회계상 은행 내역코드·명칭. 실제 은행 4자리 코드와 구분 |
| 業者 | vendor + bank_account | 실제 은행4자리·지점3자리·계좌·예금주·예금종류 |
| 勘定科目 | account_subject | 계정 코드·명칭·비활성화 |
| 内訳科目 | account_subsubject | 상위계정+내역코드 복합키 |

기존 44개 설계의 code_m을 은행 내역코드에 사용한다. 별도 은행기관 디렉터리를 만들거나 은행 명칭을 계좌 예금주로 잘못 대응하지 않는다. 업체의 계좌를 바꾸면 연결을 변경하며 과거 계좌 행을 삭제하지 않는다.

## 전환과 보존

새 보조 테이블 `preview_master_link`는 기존 화면 ID와 DB 자연키를 연결한다. 기존 거래의 customerId/itemId 등을 바꾸지 않는다. 초안 기본 테이블에 없는 고객 시작잔액(opening)과 상품 세율(taxRate)만 extras에 보관한다. 시작잔액/세율 이력의 최종 설계가 확정되면 정식 모델로 이관한다.

처음 시작할 때 기존 마스터 14건을 트랜잭션으로 이관한다. 기존 대상 테이블이 비어 있지 않으면 자동 덮어쓰지 않고 중단한다. 기본 데모의 내역코드101(振込手数料)은 기존 데모 분개에서 사용하는 상위계정8330으로 연결한다. 다른 내역코드는 상위계정이 없으면 이관을 중단한다.

이관 성공 후 workspace JSON에서 마스터 배열을 제거하고 `masterStorage=tables-v1` 표시 및 revision을 기록한다. 재시작 시 재적재하지 않는다. 신규 마스터 수정과 workspace revision·감사기록은 한 트랜잭션으로 처리한다. CSV 여러 행 중 오류가 있으면 전부 롤백한다. 기존 이름/코드 길이를 초과하면 자르지 않고 오류를 반환한다.

원본의 화면에 없는 필수 문자열은 신규 생성 시 빈 문자열, 필수 계산값은 0으로 채운다. 수정 시 화면이 관리하지 않는 기존 필드는 변경하지 않는다. 이 기본값은 검토용 데모 가정이며 본 이관 정책을 대체하지 않는다. 원본 삭제 플래그는 이 데모에서 0=유효, 1=무효로 사용한다.

등록 이후 코드와 복합키 소속 변경은 차단한다. 새 마스터 등록 후 기존 마스터 비활성화 방식으로 처리한다. 개별 마스터를 보호하기 위해 서버 모드의 전체 데모 초기화는 차단했다. 브라우저 저장 모드는 기존 초기화 동작을 유지한다.

## 검증

`server/masters.integration.test.mjs`는 별도 MySQL 테스트 DB에서 이관, 기존 거래 ID 보존, 실제 테이블 수정, 현장/상위계정 관계, 업체 계좌, 비활성화, CSV 롤백, 동시 수정, 재시작 및 DB 조회 원천을 검사한다. 운영 DB에서 실행하지 않는다.

향후 Java 서버에도 동일한 데이터 규칙을 적용하되, 현재 구현은 기존 웹 데모의 Node API다. 운영 데이터 직접 SQL 수정은 API의 revision 제어를 우회하므로 승인된 관리 절차가 필요하다.
